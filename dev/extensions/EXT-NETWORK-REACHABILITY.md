# 网络可达性与蜂窝网络状态修复

## 现象

蜂窝网络下局域网地址通常不可达。旧实现虽并行探测多个地址，却按局域网、手动地址、公网 IPv4、IPv6 顺序等待，导致可用公网地址也被较慢的失败候选拖住。默认网络切换时，旧网络回调还会直接将所有主机标为离线。

## 修复

- 自动模式将上次成功的活动地址加入并行竞争，并在探测成功时优先复用。
- 多地址探测收到第一个有效主机响应即返回；全部失败时仍等待所有候选结束。候选启动顺序不变，以维持重复地址的优先级。
- 用户固定的地址仍优先尝试；固定地址失败后回退到自动地址探测。
- 网络变更将主机置为 UNKNOWN、清空连续失败计数并唤醒轮询线程；旧网络丢失但新默认网络已接管时忽略该事件。
- OFFLINE 仍由现有连续主机探测失败门槛决定，网络回调本身不再判离线。

## 请求取消与单飞（第二轮）

- `NvHTTP` 记录当前 OkHttp `Call`，新增 `cancel()`；取消后立即中止连接/读取，而不是等 7 秒读超时。
- 每条地址探测持有自己的 `NvHTTP` 句柄；首个地址成功、停止轮询、删除主机、网络切换时取消其余探测。
- 每轮探测结束后最多等待 600 ms 让被取消的探测线程退出，避免旧请求残留阻塞下一轮。
- 每条地址探测记录耗时与结果（成功/失败/取消），便于在 logcat 中定位慢在哪个地址。

## 首页状态未刷新（第三轮）

症状：一直卡在「检测中」，按 Home 再回到应用后立刻显示正确状态。

根因有三条，均会导致"探测结果已得到，但首页没收到"：

1. `runPoll()` 在探测成功但数据库里查不到该主机时直接 `return false`，此时内存状态已是 ONLINE，却永远不会回调首页。现在改为跳过持久化、继续回调。
2. 轮询线程里任何 `RuntimeException`（如数据库写入失败）都会杀死线程，`tuple.thread` 被置空后无人重启，主机永久停在最后状态。现在捕获并记录异常后继续循环，并在 `refreshComputers()` 中复活已死的轮询线程。
3. 首页轮播在"交互中"会把主机更新暂存到 `pendingComputers`，若滚动状态回调丢失则永不落地；而且过期的暂存数据可能在稍后覆盖更新的状态。现在应用新数据前清空暂存，并在 `onLayout()` 中兜底冲刷一次。

## 验证

- Java 结构检查通过，`git diff --check` 通过。
- GitHub Actions 负责运行 `assembleNonRootDebug`。
- 真机验证 Wi-Fi、蜂窝网络、两种网络切换，以及关闭所有网络后的连续失败离线判定。
- 观察 logcat：`Probe <地址> ...` 与 `No DB row for ...` / `Polling ... failed:` 可定位剩余问题。
